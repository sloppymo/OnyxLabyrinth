# Agent Notes for OnyxLabyrinth

This file exists to help the next LLM/AI IDE get oriented quickly and avoid the same regressions that have been fixed multiple times.

## Project basics

- **Stack:** TypeScript, Vite, vanilla HTML/CSS/Canvas.
- **No framework.** The UI is hand-drawn DOM + a 2D canvas corridor renderer.
- **Entry:** `src/main.ts` bootstraps the app and mounts it into `#app`.
- **Build:** `npm run build` (runs the app TypeScript check, the tools/editor TypeScript check, then `vite build`). Both TypeScript checks must pass with zero errors.
- **Full verification:** `npm run check` runs `test:typecheck`, `build`, `test`, `floor:validate`, and `floor:export-check` in one sequence. Use this as the required gate before committing.
- **Dev server:** `npm run dev`.
- **Tests:** `npm test` (runs Vitest). Test files use `.test.ts` suffix and are excluded from the build tsconfig.
- **Production preview:** `npx vite preview --port 5176 --base /OnyxLabyrinth/`.
- **Deployment:** GitHub Actions builds `dist/` and deploys to Pages on every push to `main` (`.github/workflows/deploy.yml`). Deploy = `git push`. `docs/` is documentation-only — never copy `dist/` into it. Local check: `npx vite preview --port 5176 --base /OnyxLabyrinth/`.
- **Repo hygiene (2026-07-19):** `assets/`, `playtest-screenshots/`, `vfx-audit/` are local-only (gitignored, purged from history — see `docs/superpowers/specs/2026-07-19-repo-hygiene-history-purge-design.md`). Root `*-preview.html` files are generated by `scripts/generate-*.mjs`/`.ts` and gitignored; regenerate on demand.
- **Product / playtest docs:** Before balance, combat-UX, or perk work, read [`docs/AGENT-READING-LIST.md`](docs/AGENT-READING-LIST.md) for which reviews/specs are current vs stale.
- **Sprite art:** Before generating or replacing enemy/summon strips, read [`docs/SPRITE-ART-GENERATION-GUIDE.md`](docs/SPRITE-ART-GENERATION-GUIDE.md). For maze event / dungeon floor props (chests, altars, hazard markers — not combat strips), use [`docs/MAZE-EVENT-SPRITE-PROMPT.md`](docs/MAZE-EVENT-SPRITE-PROMPT.md). Raw image-generation output is never a shipping sprite; follow its source-scale, chroma cleanup, framing, anchor, and validation workflow.

## Git workflow

1. **Build before committing.** Always run `npm run build` and confirm zero TypeScript errors before `git commit`. The build is the minimum verification gate.
2. **Verify before pushing.** Do not push claims you haven't checked. For renderer/combat changes, run the game in a browser and inspect the relevant screen.
3. **Deploy by pushing.** Pushing to `main` runs the Actions deploy. Do NOT copy `dist/` into `docs/` — build output is CI-produced since 2026-07-19.
4. **Commit message style.** Use conventional commits: `feat(scope):`, `fix(scope):`, `perf(scope):`, `chore(scope):`, `docs(scope):`. Keep the summary under 72 characters.
5. **No debug code in commits.** Remove `console.log`, `window.__` exposures, `debugger`, and temporary timing hooks before committing.
6. **Do not mutate git history unless asked.** No `git rebase`, `git reset --hard`, or force-push without explicit user confirmation.
7. **Parallel sessions share one working tree.** Scope every destructive git op (`git restore`, `git checkout --`, `git clean`, blanket `git add -A`) to **explicit paths** you own in this session — never `git restore src/` or similar. Before committing a shared file (especially `src/styles.css`), diff it against `origin/main` and keep unrelated in-flight / already-deployed styles. Prefer `git push origin HEAD:main` (or a feature branch) over `git checkout main` when another session has uncommitted work.

## Hard rules

1. **Do not change game logic** (movement, collision, combat math, encounter rates, map data) unless the user explicitly asks for it.
2. **Do not remove existing visual effects:** fog falloff, amber glow lines, vignette, CRT scanlines.
3. **Do not change the perspective/vanishing-point math** in the corridor renderer unless asked.
4. **Renderer changes must be verified visually.** After any change to `src/engine/renderer.ts`:
   - Run `npm run build`.
   - Start the production preview.
   - Capture screenshots of at least: straight corridor, open side passage, front wall, darkness zone.
   - Inspect for black walls, missing ceiling, center seams, or texture stretching.

## Common pitfalls

- **`#message` overlay:** The message box is absolutely positioned over the top 35% of the viewport. When empty it must be hidden (`display: none` / `visibility: hidden` / `opacity: 0`) or it covers the ceiling with a black box. `shell.setMessage()` handles this.
- **Texture cache:** `renderer.ts` caches one prepared tileset per floor id in `tilesetCache` (loaded by `loadTextures()`, selected by `state.floor.id` each frame; floors without art fall back to the floor-1 set). If any image fails, the cached set holds `null` for that slot and the renderer silently falls back to gradients/fills. Check the browser console if a texture seems missing. Tileset PNGs are generated by `scripts/generate-floor-tilesets.mjs` (deterministic; re-run it to regenerate `src/assets/f*_*.png`).
- **CanvasPattern lifecycle:** `CanvasPattern` objects are tied to a specific canvas context. When the canvas bitmap is reset (e.g., `canvas.width = ...` in `shell.resizeCorridorCanvas()`), cached patterns become invalid and draw as black/transparent. Do not cache `CanvasPattern` objects across frames; recreate them inside the draw call.
- **Dungeon lighting is shared intent, not identical fog math.** `LIGHTING` in `render-math.ts` is the palette + near-warm + pool model both maze backends read. Canvas still uses `opacityForDepth` with a *depth-graded fog target* (`fogColorForDepth`: warm `{14,13,10}` → cool `{8,10,14}`). WebGL uses Three `FogExp2` whose color is simply `fogFar`. Do not retune one backend to match the other's extinction numbers. WebGL pool colors are **constant per compiled quad** (centroid sample stamped on all four vertices) so GPU interpolation cannot paint a smooth modern gradient across a pixel wall. Door/stair panels use `poolDoorGain` (0.25), not full exclusion.
- **Canvas sizing:** The canvas intrinsic size is kept in sync with the CSS container by `shell.resizeCorridorCanvas()`. Do not set `canvas.width`/`height` to fixed values elsewhere.
- **Display state:** `main.ts` previously toggled `viewportWrap`, `canvas`, `map-canvas`, and `combat-panel` visibility in many places. The single source of truth is now `shell.showMode()`.
- **Far-to-near rendering:** The renderer collects per-depth draw commands and executes them far-to-near. Do not insert raw drawing calls inside the forward visibility walk without pushing them into the command list.
- **Front-wall depth 0:** All front-facing wall quads, including the closest one, are textured. Avoid special-casing `depth === 0` to skip the texture fill; that produces a black hole where the wall should be.
- **Trap prompt modality:** while `state.pendingTrap` is set (party standing on a trapped chest), every dungeon input handler in `main.ts` is gated off with `!state.pendingTrap` and a dedicated keydown listener owns I/D/O/L (+Esc = leave). Any NEW dungeon key handler must add the same gate or it will fire mid-prompt.
- **#message length:** the message overlay shows ~2 lines of ~30 characters before clipping (it scrolls, but players won't). Keep interactive prompt strings (key hints) short enough to stay visible.
- **Borrowed "title" mode:** the actual title screen (`title-ui.ts`) owns mode `"title"` at boot, but the save menu (Esc), the dungeon spell menu (G), the NPC panel, the post-combat perk selection overlay, the New Game prologue (`prologue-ui.ts`), and the wish/ending screen (`ending-ui.ts`) all *also* borrow it to pause dungeon/combat input. Every consumer's key listener guards on its own controller instance being non-null, so they can't fight each other — but any NEW overlay borrowing "title" must follow the same pattern (own controller + a `justOpened*` flag so the keypress that opened it doesn't immediately drive it too). `EndingController` has two possible synchronous-open call sites (the combat result confirm, and the perk overlay's `onDone`), not just one — its `justOpenedEnding` listener in `main.ts` is registered after both.
- **Synchronous mode open mid-keydown:** multiple independent `window` keydown listeners each guard on `state.mode`. If listener A opens mode B *inside the same keydown dispatch*, listener B (registered later) sees the new mode and can immediately act on that same keypress. This skipped the Game Over screen on every wipe confirm until `GameOverController` armed after a macrotask (`setTimeout(0)`). Prefer a `justOpened*` / `suppressNext*` / controller-side arming guard whenever a key handler constructs a new input-bearing mode — do not rely on `stopPropagation` alone.
- **Utility spells are dungeon-only:** spells whose effect kind is light/levitation/detect must stay out of combat spell lists (`isUtilitySpell` filter in combat-ui.ts `knownSpells`) — the combat resolver has no case for them and would silently waste the turn and SP.
- **Trinket items** (`type: "trinket"`, e.g. ring-of-water-walking) are carried, never equipped and never shop stock. Auto-equip paths must only handle `weapon`/`armor`; the shop buy list filters trinkets out. Their effects are checked directly by game logic (`inventory.some(e => e.itemId === ...)`).
- **Inventory is `InventoryEntry[]`** (`{ itemId, identified }`), NOT `string[]`. Chest weapons/armor drop unidentified ("Unknown Weapon", appraise at the shop for 50g); shop purchases are identified. After combat, use `reconcileInventoryAfterCombat` — never rebuild the list from counts, which destroys per-instance flags. Save format v5 migrates v4 string inventories (everything identified).
- **Cursed gear** (`ItemDef.cursed`) force-equips on pickup (`forceEquip`) and can never be displaced — `equipItem` refuses to replace a cursed item in a slot; the Temple's `[R] Remove Curse` (100g) shatters it from loadouts AND inventory. The shop refuses to buy or stock cursed items.
- **Outside-combat damage never kills:** trap and water damage floors each character at 1 HP by design — party wipes belong to combat. Keep that invariant for any new dungeon hazard.
- **Canvas paint order must use LIVE position, not home-slot position:** `combat-scene.ts`'s draw loop sorts all combatants by footY before painting (`paintOrderFootY(baseFootY, anim, now)`, ascending = farther-drawn-first). Until 2026-07-31 the sort key used each actor's static home-slot footY only, ignoring its current `ActorAnim` move offset — invisible for ordinary attacks (the mover's own offset never crosses another actor's row), but wrong for any choreography step that flings a sprite well outside its home slot (e.g. Orc's `meleeGangUp` Pack Leap leaping deep into party territory): the sprite painted in its resting z-order for the whole ~2s animation instead of its true on-screen position, a sustained ~320ms occlusion glitch on each leap phase. The Phaser backend (`combat-phaser-stage.ts`) never had this bug — `sprite.setDepth(footY)` already includes the live offset. Any new choreography step with a large offset must go through `paintOrderFootY`, not a raw static-slot lookup; `scripts/debug-choreography.test.ts` and the `paintOrderFootY` tests in `combat-scene.test.ts` are the fast (no-browser) way to check a new step's ordering across its whole timeline before trusting a screenshot.
- **An uncaught throw inside the Phaser scene's `update` freezes the battle screen forever.** Phaser's `RequestAnimationFrame.step` calls `callback(time)` and only *then* reschedules — so one exception escaping `scene.update` kills the render loop permanently. It does not look like a crash: `CombatController`'s own RAF (`combat-ui.ts` `startRenderLoop`) and the DOM menus keep running, so turns still resolve and menus still respond while the canvas is a frozen still. This shipped once (fixed 2026-08-01): `Phaser.Actions.AddEffectShine` registers its own `sprite.on("destroy", tidyup)` that destroys the Shine's tween + DynamicTexture, and `clearShine` disposed those same resources early without unhooking it; the next `sprite.destroy()` (pool prune in `syncActors`, strip/fallback swap, teardown) re-entered `DynamicTexture.destroy()` after `Texture.destroy()` had nulled `manager` → `Cannot read properties of null (reading 'stamp')`. Any Phaser effect that self-registers cleanup must have that listener removed when you dispose it by hand — `syncHealShine` diffs `sprite.listeners(DESTROY_EVENT)` around the `AddEffect*` call to capture the exact handler (stored for `clearShine`). `scripts/playtests/arena-freeze-verify.mjs` is the repro: it hashes screenshots during playback, and a frozen canvas shows up as 1 distinct frame out of 10.
- **Corridor billboards: tile features project their OWN cell, never a `RayHit`.** `castRay` returns the cell it stepped *into* whose entry edge blocked — i.e. the cell on the far side of the wall. The old `drawDepthFeature` keyed off `hit.mapX/mapY`, so it painted feature glyphs onto walls for cells the party cannot see and never drew a chest sitting on open floor ahead; features were effectively invisible until you stood on them. `drawFeatureBillboards` now projects each feature tile through the same `projectBillboard`/`placeBillboard` path as `drawMapSprites` (perspective scale, far-to-near sort, wall Z-test, fog + darkness alpha). Add new world-space corridor markers there, not to the per-strip wall loop. The Z-test samples a **single** strip at the billboard's centre x, so a very wide billboard can still bleed past a wall edge — that limit is inherited, not new.
- **Shipping a corridor prop is a two-line change — no code edit.** `data/maze-props.ts` maps each `TileFeature` to sprite ids in **preference order**; the corridor draws the first id that resolves in `MAP_SPRITES` and falls back to the text glyph when none does. To ship art: drop the cleaned PNG in `public/assets/map-sprites/` and add its `MAP_SPRITES` entry. Naming art that does not exist yet is deliberately safe (the lookup misses), so that table is also the work queue. Ids track the asset map in `docs/MAZE-EVENT-SPRITE-PROMPT.md`. **`chest-unlocked` shows a chest heaped with gold, so it marks an UNLOOTED chest** — never reuse it for an emptied one or it advertises loot the party already took.
- **A looted chest keeps its tile and goes inert.** Emptying a chest used to `tile = undefined` in three places, erasing the landmark; a cleared wing then looked identical to an untouched one. The tile now survives (emptiness lives in `TreasureDef.itemIds`, via `isTreasureLooted`), and `handleTileFeature` short-circuits on it *before* the switch — returning `null` and clearing the darkness/antimagic flags, exactly like bare floor. Without that guard, re-crossing an emptied chest would re-message every step and strand zone flags. Encounters still roll on the tile (a treasure result never early-returns in `onMove`), so this is not an encounter-rate change. Until `chest-open` art ships, a looted chest deliberately draws **nothing** — same as the old behaviour, rather than a `$` promising loot that is gone.
- **Feature markers are clamped; decor sprites are not.** `featureMarkerSize` (`render-math.ts`) clamps a marker to `FEATURE_MARKER_MAX_SCREEN_FRAC` of screen height. Decor keeps the raw perspective scale because a barrel is a physical object and *should* fill the view up close; a glyph at that size reads as a UI failure instead (unclamped it covered ~46% of the viewport one tile out). Don't "fix" the clamp away, and don't extend it to decor.
- **Map-decor PNGs ship without alpha and must be keyed at load.** `public/assets/map-sprites/{torch,crate,bones,barrel}.png` are colour-type-2 RGB with a baked `20,18,16` background and **no** `tRNS` chunk, so `ctx.drawImage` painted an opaque box around each prop (alpha-blended by `opacityForDepth`, so it read as a dark halo far away and a hard black rectangle up close). `map-sprite-cache.ts` runs each loaded image through `keyOutBackground` (`sprite-alpha.ts`) and caches the result as its own `HTMLCanvasElement`. Two rules: the flood fill starts from the **border** so an enclosed pocket of the background colour survives, and images that already carry alpha (`chest-unlocked.png`) are skipped untouched. Cache the derived **canvas**, never a `CanvasPattern` — see the CanvasPattern pitfall above.
- **NPCs are additive content only:** dungeon NPCs (`FloorDef.npcs`, tile `"npc"`) give hints, barter, and flavor — they must never gate campaign progression (keys, stairs, boss access). Their combat identities (`combatEnemyIds`) must reference enemies with real sprite strips in `sprite-manifest.ts`; NPC-only enemies use `floors: []` to stay out of random encounter tables. Stepping onto an npc tile opens the panel INSTEAD of rolling an encounter (`result.npcId` early-returns in `onMove`). Kills persist via `state.killedNPCs` — both `transitionToFloor` and save-load must run `applyKilledNPCs` on the fresh floor clone.
- **Never author a room flush against a floor's absolute grid edge (row/column 0 or the max index).** `drawFloorCeilingCast`'s per-scanline floor/ceiling raycaster (`renderer.ts`) samples world position from screen-row distance alone, not actual wall hits — for scanlines near the horizon that projected sample can land one cell past the grid array's boundary. `cellTextures[gy]?.[gx] ?? primaryTextures` then silently falls back to the floor's *default* tileset with no error or warning, so a room built on the last row/column can render the wrong theme in exactly the spot you're least likely to screenshot-check (near a back wall, at the horizon). This shipped once in Hot Boi's Tavern (bar row placed at the map's literal last row rendered as cold f1 stone instead of warm tavern wood) and was only caught by close visual review, not by `floor:validate` or any test. Rule: always leave at least one full untouched row/column of buffer between a hand-authored room's outer wall and the array boundary, regardless of what the `tilesetZone` bounds say.
- **Check whether an NPC/tile's interaction already routes somewhere before building new interaction plumbing.** `openNPCPanel(npcId)` in `main.ts` dispatches by id to specialized controllers (e.g. `npcId === "hot-boi"` → `TavernController`) before falling back to the generic NPC panel. When wiring a new physical room to an existing UI system, check this dispatch first — Hot Boi's Tavern needed zero new interaction code because the routing already existed once his NPC id was in place; only his topic list needed merging.
- **Before reusing a shipped door/landmark's existing coordinate, verify what's actually behind it, not just that the sprite is already placed.** The Church of Saint Namanda's hero door shipped once (`b64a6f5`) on the cut-bell-chapel↔ember-suture junction at (10,10)/(11,10) — a real, live through-corridor carrying unrelated Floor 1 traffic, not a dead end. Building the room directly behind it would have either re-themed a shared junction tile (a flash of pale stone for one step, then back to ember stone — reads as a texture glitch) or required rerouting existing connectivity. The fix (`agent/saint-namanda-church`) was relocating the door — same sprite, same symbol, not regenerated — to the room's own mouth one cell over, confirmed in-engine both that the new spot gives an immediate material transition and that the vacated junction still connects everything it used to. Rule: "the art is already there" is not the same question as "is the space behind it actually free" — check the grid, not just the doorFeatures entry.
- **`propBillboardSize` (`render-math.ts`) forces every mapSprite billboard into a square** (`ctx.drawImage(img, x, y, size, size)`), regardless of the source PNG's real aspect ratio. Existing decor (torches, barrels, Hot Boi's furniture) stays close enough to square that this is invisible; a genuinely wide-and-flat sprite (Namanda's kneeling rail, originally cropped to 52×18, ~2.9:1) gets stretched vertically into a distorted, muddier-colored blob at typical viewing distance. Fixed art-side this time (padded the source to a squarer ~1.6:1 canvas, matching `hotboi-bench`'s own ratio) rather than touching the renderer. **Renderer debt, not yet fixed:** the ceiling-sprite path already preserves aspect ratio; `propBillboardSize`'s floor-standing path does not. Keep new `mapSprite` art within roughly 1:1–1.8:1 until someone gives `drawMapSprites` an aspect-aware size (separate width/height, ceiling-sprite-style) — don't rediscover this by shipping another wide prop.

## Combat (FF6) verification checklist

After any change to `src/engine/combat-scene.ts`, `src/engine/combat-choreography.ts`, `src/engine/combat-phaser-stage.ts`, `src/engine/combat-ui.ts`, or `src/engine/combat-select-action-view.ts`:

**Presentation backends:** combat paint is a `CombatStage` (`combat-stage.ts`). **Phaser is the default** (dynamic `import("phaser")` → `#combat-phaser-canvas`). Rollback with `?phaser=0` (canvas painter in `combat-scene.ts`). Choreography (`playTurn` / `updateScene`) lives in `combat-choreography.ts` and is shared. Do not import `combat-phaser-stage.ts` from tests (jsdom).

1. **Combat starts:** entering a fight shows the FF6 scene (enemies LEFT, party RIGHT) with the three blue bottom windows (action menu / enemy names / party HP list) overlaid on the canvas.
2. **Party sprites animate:** party members are animated pack sprites (Knight/Wizard/Priest/Archer/Swordsman) facing LEFT, idle-looping; the acting character has a bouncing marker. Summoned allies reuse enemy strips but are drawn mirrored (also face LEFT toward the enemy line).
3. **Turn playback:** confirming an action plays immediately — attacker walks forward, attack animation, target hurt animation + white bouncing damage number, walk back. No Space-gating during playback.
4. **Damage popups:** white = damage, green = heal, purple = poison tick, "MISS" on evades.
4b. **Dialog barks:** cream text above sprites on cast shout / party heavy hit / death — sibling channel to damage popups; scales with playback speed; cleared on skip; muted via `__onyxDebug.setBarksEnabled(false)`.
5. **Spell banner:** casting shows the spell name in the top banner window plus a burst effect on targets.
6. **Target cursor:** in target selection, a blinking marker appears over the highlighted candidate on the scene; the menu window lists names with ▶.
7. **Image-strip enemies:** enemies with strips (e.g. `failed-experiment`, `lesser-construct`) render the PNG facing RIGHT (toward the party); unmapped enemies use the procedural fallback.
8. **Defeated fade:** killed enemies play their death strip then fade out; KO'd party members stay in the death pose.
9. **Result window:** victory shows gold/XP in a centered window; Enter exits.
10. **Combat → dungeon transition:** fleeing or winning returns to the dungeon view with corridor textures intact.
11. **Windows never clip sprites:** all four party members (`PARTY_SIZE`) and all enemies stay visible above the bottom windows.
12. **Summoned allies in the windows:** living BAMORDI/SOCORDI summons show as cyan rows in the enemy window (name + HP) and as compact cyan rows below the party list; single-target heal spells list them as extra targets (cursor kind "ally" on the scene) and the heal resolves on the summon's HP.

## Debug/testing aids

- **`scripts/debug-choreography.test.ts`**: a text-only, no-browser harness for debugging combat animations — run it in isolation (`npx vitest run scripts/debug-choreography.test.ts --reporter=verbose`, the flag is required or Vitest swallows the `console.log` output). It drives a real enemy turn through the actual AI resolver (`resolveEnemyTurn` — not hand-rolled `CombatEvent`s) and the real choreography engine (`playTurn`/`updateScene`), printing every actor's state/offset/popup/banner at each scheduled `ChoreoStep`. Use this first when building or debugging any new attack animation (especially a coordinated/multi-actor one — see "Combat event system" above); it catches logic/timing/z-order bugs at a fraction of the cost of a browser screenshot loop. Reserve an actual Arena/`?debug=1` browser pass for a final visual confirmation once the trace looks right, not for iterating on the animation itself.
- **Arena mode** (`engine/arena-ui.ts`, mode `"arena"`, reachable from the title screen's `[A]` option): fights back-to-back encounters outside the dungeon for fast manual combat/perk verification without navigating floors. **Not debug-gated** — it's a normal, always-available title-screen option regardless of `?debug=1`, and it awards real party gold/XP through the same `endCombat` path as dungeon combat (see "Enhancement tiers and shop pricing" above). Treat it as a legitimate in-game farming loop when reasoning about economy/balance, not just a dev tool.
- **`?debug=1` query param**: exposes `window.__onyxDebug` with the live `state`, `startCombat`, `exitDebugCombat(result)` (force-ends the active combat with a given result — `"victory"`/`"wipe"`/`"fled"` — and runs the real `endCombat` flow, so post-combat level-ups/perk-queue logic still fires), plus encounter/loadout helpers. Useful for scripting a browser session straight to "XP high enough to hit a perk tier, then force victory" instead of manually grinding fights. Never used in normal play; strip nothing here, it's already gated behind the query param. **Wipe path clears combat** (`state.combat` / `combatController`) before `openGameOver()` — same as fled/victory — so `jumpTo`/`loadSave` work immediately after a wipe (fixed 2026-07-25; do not re-open as a stale-combat bug).
- **`__onyxDebug.snapshot(opts?)`** (`src/debug/snapshot.ts`, also aliased as `window.render_game_to_text()` returning the same object JSON-stringified): the structured state dump Playwright playtests should read instead of scraping pixels or hand-building their own `page.evaluate` dumps. Returns mode, **`route`**, floor, position + compass, tile, flags, party, inventory, gold, keys, buffs, message text/visibility, a combat view (exact enemy HP — debug-only; players see descriptors), and **`availableActions`** (the legal input verbs right now). `opts.map` adds an ASCII map render (`opts.mapRadius` limits it to a window around the party); the grid is omitted otherwise because it's large.
  - **Always read `route`, never bare `mode`, to tell which screen is live.** The save menu, grimoire, NPC panel, and perk overlay all borrow mode `"title"` — `route` is what distinguishes them. It comes from `resolveControllerRoute(currentRouteFlags())`, the *same* flag builder the real input router uses, so the debug surface can't drift from actual input routing. If you add a new overlay, extend `currentRouteFlags()` in `main.ts` (one place, both consumers).
  - The pure builder (`buildSnapshot`/`availableActionsFor`/`asciiMap`) has no DOM or engine imports and is unit-tested in `src/debug/snapshot.test.ts`; `CombatController.debugView()` and `shell.getMessageText()` are the only engine-side seams feeding it. `snapshot().idle` reports the quiescence check below.
- **`__onyxDebug.isIdle()`**: true when nothing is animating that a script should wait out — no pending mode fade (`transitionToMode`'s 150ms opacity swap, tracked by `modeTransitionPending`), no render-camera tween (`isRenderCameraAnimating()`), no prologue auto-play, no combat encounter/leave transition (`combatTransitionActive`, including Phaser stage boot), and no unfinished combat playback choreography. Menus, camp, town, and combat's non-playback phases (palette/select*/result) all count as idle-awaiting-input on purpose — this is "is it safe to read state / press the next key," not "is the player doing nothing." The decision logic is the pure, exhaustively-unit-tested `computeIdle()` in `src/debug/idle.ts` (`src/debug/idle.test.ts`); `main.ts`'s `isIdle()` is a thin call with live values, and `CombatController.isChoreographyDone()` is the cheap (no array-copy) combat seam feeding it — don't call `debugView()` from a polling loop, it allocates enemy/log arrays every tick.
- **`__onyxDebug.readiness()`**: boot/asset-load status for scripts that want to wait past the first splash. `fonts`/`textures`/`enemySprites`/`partySprites`/`effectSprites`/`mapSprites` are booleans meaning "settled" (true on both success and failure — the specific name lands in `failed` on failure, not the boolean). `audioUi`/`audioCombat`/`audioDungeon` are `"not-started" | "loading" | "done"` instead, because — see the note below — those three don't start loading at boot at all.
  - **Audio is not fully procedural; three WAV sample families can fail to load, silently, and that's now observable.** `engine/audio.ts` fetches `UI_SFX_FILES`/`COMBAT_SFX_FILES`/`DUNGEON_SFX_FILES` (`public/assets/sfx/{ui,combat,dungeon}/*.wav`) via `fetch` + `decodeAudioData`, kicked off by `loadUiSounds()`/`loadCombatSounds()`/`loadDungeonSounds()` from `resume()` — which only runs on the *first user keydown* (autoplay policy), not at page load. A 404 or decode failure leaves that cue's buffer empty and `playDungeonSfx`/`playCombatSfx`/the private UI player just no-op on the next call — no exception, no console line. `audio.getSampleLoadStatus()` is the read-only accessor `readiness()` wraps (`{ ui, combat, dungeon, failed: string[] }`, ids like `"ui:cursor"`); **never call `load*Sounds()` from a status probe** — it calls `resume()` when there's no `AudioContext` yet, which would both create one outside a user gesture and race a second fetch against an already in-flight one. Only the ambient drone/footsteps/door-open/torch-jitter layer is procedural; this only applies to the sample-backed SFX layer.
- **`__onyxDebug.jumpTo(opts)`** / **`dumpSave()`** / **`loadSave(json)`**: setup accelerators for playtests. `jumpTo({ floorId, x, y, facing?, partyLevel?, gold?, keys?, items?, autosave?, stepsSinceEncounter?, clearUnlockedDoors? })` routes through the real `transitionToFloor` (so killed NPCs, loot, unlocked doors, and `deepestFloorReached` stay consistent — unlike the old hand-rolled `warp()`). Refuses while combat or an overlay/hub controller is live. `autosave` defaults to `true` (same as normal floor transitions); pass `false` so a `loadSave` → `jumpTo` → Continue test does not clobber the autosave slot. `dumpSave`/`loadSave` wrap `serialize`/`deserialize` plus the Continue-path mode normalization (`normalizeLoadedMode` in `src/debug/load-normalize.ts`). Party leveling in jumpTo mirrors Arena (`levelUpChar` loops — see `applyJumpPartyOptions` in `src/debug/jump-to.ts`).
- **`__onyxDebug.log(n?, kind?)`** / **`clearLog()`** / **`sounds(n?)`** / **`soundsPlaying()`** — the evidence layer. `snapshot()` says what is true *now*; the event ring buffer (`src/debug/event-buffer.ts`, 500 entries, `seq` never resets so dropped-past-capacity gaps are detectable) says what happened just before. Kinds: `modeChange`, `route`, `message`, `feature`, `audioCue`, `error`, `assetFailed`. Combat is deliberately absent — it already has structured `CombatState.events`.
  - **Chokepoints, all no-op unless `?debug=1`:** `shell.setDebugMessageHook(fn)` is the single seam for message writes (don't poll `#message`); `main.ts`'s `recordDebugEvent` covers `transitionToMode` and `onMove`'s feature result (the stepped-on tile is captured *before* `handleTileFeature`, which can move the party to another floor); `route` has no single call site, so it's **sampled** after every keydown and on every `snapshot()` rather than instrumented per controller. Errors come from `window` `error`/`unhandledrejection` listeners registered in the same block.
  - **Audio spy** (`src/debug/audio-spy.ts`): patches the leaf emitters on the `audio` singleton — `playUi`/`playCombatSfx`/`playDungeonSfx` plus the procedural `footstep`/`doorOpen`/`doorLocked`/`levelUp`/`uiTextTick`. Only leaves, because the friendly wrappers (`uiConfirm`, `uiCancel`, …) all delegate to `playUi` and patching both would double-count. Each record is `{ id, firedAt, durationMs, endsAt, bufferMissing }`; ids are namespaced `ui:`/`combat:`/`dungeon:`/`proc:`. Sample durations come from the decoded `AudioBuffer`; procedural ones from the `PROCEDURAL_CUE_MS` catalog (read off the oscillator stop times in `audio.ts` — keep it in sync if you retune an envelope). **`bufferMissing: true` is the point of this whole thing:** a failed WAV is a silent no-op, so this is what tells "cue fired but was inaudible" apart from "cue never fired." Caveat: `proc:` cues record the *invocation*, and `uiTextTick`/`uiCursor` rate-limit internally, so a suppressed repeat still appears.
  - **`assetFailed`** events are diffed out of `readiness().failed` (which `readiness()` and `snapshot()` both sync), so a 404'd sample surfaces once, by id, instead of never.
  - **`snapshot().warnings`** comes from `src/debug/invariants.ts` (pure, unit-tested): hp/sp bounds, `activeCharIds` unknown/duplicate/wrong-count, `pendingTrap` outside dungeon mode, combat-view/route disagreement, enemy hp bounds. Empty array means self-consistent. Add a check here rather than re-asserting the same thing in every playtest script. `snapshot().soundsPlaying` lists cue ids whose envelope hasn't elapsed.
- **`scripts/playtests/lib.mjs`**: shared Playwright helpers — `launch()` (with console/pageerror/requestfailed capture), route-driven `bootToDungeon(page, url)`, `boot(page, url, { scenario })` (title → `jumpTo`, skips prologue/party-creation), `jumpTo(page, opts)`, `snap(page)` / `snapWithMap(page, radius)`, `waitForIdle(page, timeout?)` (polls `isIdle()` every ~30ms instead of a fixed sleep), `act(page, key, timeout?)` (press then `waitForIdle`), `press`, `shot`, `debugLog`, `sounds`, `captureFailureBundle`, `getTranscript`, `createFindings`, `writeReport`.
  - **`captureFailureBundle(page, name, { outDir, errors })`** writes `bundle-<name>-<ts>.png` + `.json` holding the screenshot, a full snapshot (with map), `log(300)`, `sounds(80)`, `readiness()`, the browser console/network errors, and the **action transcript** — every `press`/`act`/`jumpTo`/`boot` this library drove, recorded automatically in a `WeakMap` keyed by page. It never throws; a broken capture must not mask the finding that triggered it. PR-5 adds a seed + per-step state hash to make those transcripts replayable; today they are evidence only.
  - `createFindings({ page, outDir, errors })` auto-captures a bundle for each P0/P1 finding. `find()` stays synchronous (existing call sites unchanged) and queues the capture; **`await findings.flush()` before writing the report** or captures may be cut off by `browser.close()`. Because the script keeps running during a capture, a bundle can reflect state a beat after the finding. New playtest scripts should import these rather than re-rolling them; `bootToDungeon` reads `route` each step, so inserting a new screen into the boot flow (as the prologue did) no longer breaks every script's fixed key sequence. `scripts/playtests/smoke-debug-surface.mjs` is the smoke test for the surface itself (run against `npx vite preview --port 5176 --base /OnyxLabyrinth/`).
  - Most waits in the lib and in `playtest-floors-1-3.mjs`'s step/turn/unlock helpers now use `waitForIdle` — a real ~30% wall-clock win (measured: 93-97s vs. the old fixed-sleep version's 139s for the same run). A few waits stay fixed **on purpose**: pressing "n" into the auto-playing prologue, and the trap-prompt/menu-open/initial-page-load spots that don't route through `transitionToMode` or the render camera at all — `isIdle()` has nothing to poll there, and it would either spin for its full timeout (prologue, since it's never idle until closed) or return true instantly without proving anything (menu-cursor moves). Don't loosen `computeIdle()` to make a script's wait faster; add a script-side fixed wait with a comment instead, the way these do. Do **not** reintroduce a private `warp()` — use `jumpTo`.
  - **Step-on event / tile message assertions:** `onMove` sets the feature message *before* rolling a random encounter. If a fight starts on that same step and the script flees via `exitDebugCombat`, the live message band becomes `"You fled from combat."` even though the event fired. Assert against recent `__onyxDebug.log(n, "message")` entries (see `recentMessages` in `playtest-floors-1-3.mjs`), not only `snapshot().message.text`.
  - **Campaign encounter zones are frequency-only** unless a zone sets `tableFloorId` (none currently do). Safe/hot share `ENCOUNTER_TABLES[floor.id]`; only `rateMul` differs. Pity still forces a fight by step 28 even at `rateMul: 0`. See `docs/playtests/2026-07-25-invariants-pacing-playtest.md` addendum. Session handoff: `docs/FOLLOWUP-2026-07-25-SESSION-HANDOFF-PROMPT.md`.
  - **Boss identity is display-name-only; internal ids are historical.** `headmasters-echo` / `-remnant` / `-ascendant` are **The Dead Boy** (F3), **The Lonely Girl** (F4), and **The Crying Man** (F5). Ids are frozen for save/test stability and carry **no lore** — do not rename them, and do not reconstruct fiction from them. Retired display vocabulary that must never come back: *Headmaster*, *Echo* (as a player-facing noun), *the Vanguard's/Choir's/Drowned Echo*, *the First Descent*. Canon: `docs/superpowers/specs/2026-07-25-labyrinth-narrative-design.md`.
  - **Boss BGM is authored; boss sprites are reused.** The boss fight music is `public/assets/music/higher-difficulty-battle.mp3`. All three bosses reuse existing sprite strips at `BOSS_SIZE`. `audio.startBossCombat()` streams the authored music; `main.ts` starts it only when `combat.isBoss` and stops it unconditionally in `endCombat`, so a normal fight cannot inherit it.

## Architecture overview

The practical boundary is **rules/content** (`src/game/`, `src/data/`, `src/content/`) versus **browser presentation** (`src/engine/`). `src/main.ts` owns the single `GameState`, mode transitions, and per-mode controller lifecycle.

- **Application modes** are a strict union (`title | party_creation | town | dungeon | combat | camp | game_over | arena`). `shell.showMode()` is the only place that should toggle top-level DOM visibility. Several overlays (save menu, spell menu, NPC panel, perk selection) borrow mode `"title"` to pause dungeon input. Borrowing "title" is risky: always restore the real previous mode and never trigger title-music logic from an overlay.
- **Dungeon rendering** (`src/engine/renderer.ts`) draws the pseudo-3D corridor. `src/engine/render-math.ts` holds the pure, unit-tested geometry/fog/camera math. `src/engine/camera.ts` handles movement, turning, and door unlock. `src/engine/automap.ts` and `src/engine/map-overlay.ts` are the full (`M`) and quick (`V`) maps.
- **Combat** is split into rules, choreography, and two painters. `src/game/combat.ts` resolves a turn and emits `CombatEvent`s. `src/engine/combat-choreography.ts` builds the timed animation state. `src/engine/combat-phaser-stage.ts` is the default painter; `src/engine/combat-scene.ts` is the `?phaser=0` Canvas rollback. `src/engine/combat-ui.ts` drives the per-actor FF6 menu. Both painters consume the same choreography; never add a second choreography engine.
- **Party / perks / leveling**: `src/game/party.ts` defines `PARTY_SIZE = 4` (not six). `src/game/effective-stats.ts` is the single source of truth for final stats. `src/game/perks.ts` (`perkModifiers` for passives, `dispatchHook` for reactive). `src/game/leveling.ts` handles automatic post-combat level-ups.
- **Floors and content**: `src/data/floors.ts` contains campaign definitions, `src/content/floors/*.json` are JSON packs, and `src/game/floor-registry.ts` is the runtime resolver. `src/game/floor-validate.ts` is the linter. `FloorDef.encounterTable` is deprecated/ignored in favor of `ENCOUNTER_TABLES[floor.id]`.
- **Audio** (`src/engine/audio.ts`) streams music and plays sample-backed SFX plus procedural cues. Music ownership is per-mode; never start mode-specific music from an overlay.
- **Save and compatibility** (`src/game/save.ts`) is at version 14. Save-compatible identifiers (enemy, item, perk, NPC, and floor IDs) must not be renamed casually.
- **RNG** (`src/game/rng.ts`) is the only source of gameplay randomness. `Math.random()` is not used for deterministic systems.

## Do not do this

- Do not add a second combat choreography engine. Both Phaser and Canvas must paint the same `combat-choreography.ts` state.
- Do not import the Canvas painter (`combat-scene.ts`) from choreography or Phaser.
- Do not add a second fog formula. `render-math.ts` owns the canonical math.
- Do not hardcode content IDs in renderer or UI code; look them up in the data modules.
- Do not casually rename enemy, item, perk, NPC, or floor IDs. They are save-compatible and test-referenced.
- Do not use `Math.random()` for gameplay randomness. Use `src/game/rng.ts`.
- Do not commit `dist/` or copy it into `docs/`. CI builds and deploys `dist/` separately.
- Do not commit purchased raw asset packs (`assets/`, `playtest-screenshots/`, `vfx-audit/`). They are local-only and gitignored.
- Do not treat a screenshot or build success as proof of visual correctness for renderer/combat changes.
- Do not bypass `shell.showMode()` when toggling mode visibility.
- Do not confuse a borrowed `"title"` mode with the real title screen.
- Do not update damage preview (`combat-preview.ts`) without also updating the actual resolver path in `combat-actions.ts`/`combat-spells.ts`.
- Do not remove a fallback renderer or debug surface that is still used by `?phaser=0`, `?debug=1`, or the test suite.

## Conventions

- Prefer `const` and explicit types.
- Keep renderer constants in `RENDER_CONFIG` at the top of `renderer.ts`.
- Keep audio constants in the `AudioEngine` `CFG` object at the top of `audio.ts`.
- Keep combat scene layout constants near the top of `combat-scene.ts`. (The old `combat-renderer.ts` was deleted in the FF6 rewrite — do not restore it from git history; `combat-scene.ts` is its replacement.)
- Renderer math functions (geometry, fog, camera interpolation) live in `render-math.ts` and are unit-tested. When adding new math to the renderer, extract it to `render-math.ts` and add a test.
- Run `npm run build` before claiming any fix is complete.
- Run `npm test` before claiming any combat/save/party/renderer-math change is complete.
- Verify visually for renderer/combat/audio changes; don't rely only on the build passing.
- **Do not copy `dist/` into `docs/`.** `.github/workflows/deploy.yml` uploads `dist/` to Pages directly on push to `main`; `docs/` is markdown design documentation only. (Older guidance said otherwise — it was wrong.)

## Class perks and effective stats

Design doc: `docs/superpowers/specs/2026-07-11-class-perks-design.md`.

- **`effectiveStats(character, loadout?, perks?)`** (`game/effective-stats.ts`) is the ONLY place combat/leveling math should read a character's stats from. It layers base `character.stats` + every equipped item's `statBonuses` + every chosen perk's `effect.statModifiers`. Nothing it computes is ever persisted — recompute on every use, including after load.
- **Two perk mechanisms, pick whichever fits a given perk's effect shape:**
  - **`perkModifiers(perks, effStats)`** (`game/perks.ts`) — for simple always-on numeric passives (damage/spell/crit/evasion/flee multipliers and bonuses, physical damage-taken multipliers with an optional front-row-only bucket, SP cost multipliers, flat bonus damage, trap disarm/damage modifiers). Folds every chosen perk into one struct; combat/features/town code reads it fresh each time, never caches it. This covers most of the 56 perks with zero combat-internals changes. `shopDiscountPercent` (Swindler) IS wired: `town-ui.ts`'s `buyPrice()` applies `discountedShopPrice(shopBuyPrice(item), partyShopDiscount(party))` — the discount multiplies the post-markup price, not the base one. (Older guidance here said this was inert; it wasn't as of this check.)
  - **`dispatchHook(hook, perks, ctx)`** (`game/perks.ts`) — for stateful/reactive perks (once-per-combat triggers, counterattacks, escalating stacks, "every Nth cast"). `CombatState.perkState` (character id → arbitrary bag) holds each character's per-combat scratch data, reset at combat start. ~19 perks have a registered handler (see the list at the top of `game/perks.ts`); a few more are wired directly in the combat engine modules (fighter-protector, thief-backstab, thief-assassin, duelist-riposte, priest-saint's regen, mage-spellbreaker, halberdier-warlord); the rest are numeric-passive or documented `// TODO(v1.1)` stubs in `data/perks.ts` whose UI descriptions carry a "(Not yet implemented — v1.1.)" marker.
- **Level-ups happen immediately after combat victory**, not at the Training Ground (`main.ts` `endCombat`): `levelUpChar` runs in a loop while banked XP covers the next level, full-restoring each time. Every level 3/6/9/12 crossed queues a `PendingPerkChoice` (kept as a **local variable in `main.ts`**, not on `GameState` — never persisted, mirrors `pendingTrap`'s policy). If the queue is non-empty, `perk-select-ui.ts`'s overlay opens (borrowed `"title"` mode) before returning to the dungeon/arena. The overlay requires an explicit ←/→ card pick before Enter confirms (per queued character) — leftover Enter spam from combat can never silently burn a perk choice; do not remove that guard.
- **Save v6** added `perkIds: string[]` to serialized characters; `save.ts`'s `migrate()` defaults it to `[]` for older saves.
- When adding a new perk: give it a `PerkDef` in `data/perks.ts` with the standard numeric `effect` fields wherever they cover it; only reach for a `dispatchHook` registration in `game/perks.ts` if the effect genuinely needs state or can't be expressed as a flat multiplier/bonus.

## Combat event system

`combat.ts` emits structured `CombatEvent` entries alongside each log message (1:1 parallel array `s.events`). The FF6 combat scene (`combat-scene.ts`) builds its turn choreography **exclusively** from these events — there is no regex log parsing anymore, and `null` events (log-only lines) are silently skipped. Consequence: when adding a new combat action or outcome, you MUST `emit()` a structured `CombatEvent` for it or it will not animate and will show no damage popup. The old round-based `resolveCombatRound` still exists (shared internals, used by tests); the combat UI uses the per-turn API.

- **Coordinated/multi-actor attacks reuse the `presentation` field, not a new event type.** Orc's Pack Leap (`data/enemy-abilities.ts`, id `pack-leap`) is the reference example: a `"cast"` event with `presentation: "meleeGangUp"` (gated by a new `AbilityCondition` kind, `minSameKind`, requiring N living enemies sharing the actor's `EnemyDef.id`). `combat-choreography.ts`'s `playTurn` branches on `evt.presentation` before its normal stationary-cast handling and calls a dedicated `push*Steps()` helper (`pushMeleeGangUpSteps`: mount an ally → leap past the front line → attack → leap back). Adding a second coordinated ability should extend this pattern (new `presentation` value + helper) rather than inventing a new `CombatEvent` variant — it stays additive and both render backends get it for free since choreography is shared. See `scripts/debug-choreography.test.ts` for a template that traces a new ability's animation headlessly (real AI resolver → real choreography, printed as text) before ever opening a browser.

## Enhancement tiers and shop pricing

- Weapon/armor lines generate `+0` through `+4` variants (`weapon()`/`armor()` in `data/items.ts`). `+0`-`+2` keep the original linear pricing (`ItemDef.price`, unchanged since before 2026-07-31) and are within normal single-playthrough gold reach. `+3`/`+4` are shop-only — `shopBuyPrice()` charges `price * 5` / `price * 15` on top of the linear price — **by design**: a dagger+4 costs 7,500g and a voidblade+4 costs 37,500g, both far beyond the ~6,300g total campaign income through floor 5 documented in `docs/superpowers/specs/2026-07-24-campaign-progression-design.md`. This is a deliberate aspirational late-game gold sink, not a balance bug to "fix" back to linear pricing — that design doc's own conclusion ("full BiS is realistically a multi-playthrough goal... the intended shape for a shop-tier-unlock sink") is exactly what `+3`/`+4` literalizes. It's reachable, not dead content, because **Arena mode is not debug-gated** (`title-ui.ts` pushes it unconditionally) and awards real gold through the same `endCombat` path as dungeon combat — repeatable Arena fights are the intended farm route to afford it.
- `+3`/`+4` gear can never appear as free chest loot: floor treasure (`FloorDef.treasures[].itemIds`) references specific item ids by hand, not a programmatic tier filter, so a floor author would have to opt in explicitly. `dropsForFloor()`/`shopInventory()` in `items.ts` are unfiltered helpers (dead code outside tests) — the real shop stock filter is `town-ui.ts`'s `getShopBuyList()` (`dropFloorTier <= maxShopTier()`, no `plus` filter), which is why `+3`/`+4` variants show up as soon as their base tier unlocks, just at the ruinous price.
- Sell/trade-in value (`Math.floor(item.price / 2)` throughout `town-ui.ts`) intentionally reads the *unmarked-up* `price`, never `shopBuyPrice()` — reselling a `+4` item recovers a tiny fraction of what it cost, which is the point of a sink, not a bug.

## Renderer performance / feel notes

- The floor/ceiling `ImageData` buffer is reused across frames (allocated once, resized only when canvas dimensions change). Do not call `ctx.createImageData()` in the hot loop.
- Edge-glow lines are batched into 4 depth-bucketed `Path2D` objects and stroked once per bucket, not per strip. This avoids per-strip `shadowBlur` state changes.
- Scanlines use a cached `CanvasPattern` instead of per-line `fillRect` calls.
- Torch flicker is a subtle warm overlay driven by a sine wave with a secondary frequency for organic irregularity. Suppressed in darkness zones. **The gradient is weighted toward the frame EDGES and is transparent at the centre, and it draws AFTER the wall pass** — both deliberate (2026-07-30). In a corridor the screen centre is the vanishing point, so a centre-weighted glow put the party's carried torch at maximum distance, and drawing it before the walls let near opaque walls occlude the light they should catch. Measured pre-fix, the near wall modulated by 0.09% of its own mean, i.e. not at all. `torchFlickerEdgeScale` (0.65) rescales the inverted gradient because it covers far more pixels than a centre-weighted one; effective alpha is ~±2.6%, and it was tuned against measured *time-averaged* frame luminance. Do not measure this effect on a single frame: `drawTorchFlicker` early-returns when its alpha goes negative, which happens every cycle, so an arbitrary-phase capture can catch a frame with no overlay drawn. Use `scripts/playtests/corridor-torch-probe.mjs`.
- **`RENDER_CONFIG` no longer declares the fog/projection/glow tunables** (2026-07-30). It spreads `MATH_CONFIG` in from `render-math.ts`, which is the copy the math functions read. `RENDER_CONFIG.fogFalloff` still resolves; there is just one definition. Previously 15 of its 38 keys were inert — 10 shadowed by the hand-copied twin, 5 with no reader at all — so editing the obvious knob silently did nothing. Add new pure-math tunables to `MATH_CONFIG`, and do **not** re-declare one in `RENDER_CONFIG`: that reintroduces the shadow.
- `Math.floor()` in the floor/ceiling hot loop is replaced with `| 0` (bitwise truncation) for performance. This is safe because world coordinates are always non-negative.
- The render camera animator (`RenderCameraAnimator` in `render-math.ts`) is module-level and DOM-free. It exposes `isAnimating()` for input gating and `reset()` for floor transitions.
- Dungeon movement input is gated by `isRenderCameraAnimating()` in `main.ts` so rapid key repeats cannot re-target an in-flight tween.
- Head bob is a screen-space integer-pixel offset applied to the floor/ceiling `putImageData` and the world-space draw pass (walls, edge glow, floor feature). Overlays (vignette, scanlines) are not shifted.
- The corridor/map canvas intrinsic size is capped at 768×672 by `shell.resizeCorridorCanvas()`; CSS scales the canvas to fill the container. This avoids multi-megapixel buffers on large/high-DPI displays.
- **Ceiling sprites (`drawCeilingSprites`) were stress-tested at 100 placements (2026-08-07)**: 100 synthetic `ceilingSprites` entries injected into a live Floor 1 session (10x10 grid, 1 cell apart, centred on the camera), measured with temporary instrumentation (reverted after the run — not shipped). Coarse box reject passed all 100 as candidates by construction (worst case: none pre-rejected); 31 survived per-billboard projection/occlusion and were actually drawn, rendering without visual corruption despite heavy overlap. Direct `render(ctx, state)` JS time was 1.83ms baseline (real Floor 1, 9 ceiling sprites) vs. 1.85ms under the 100-sprite stress fixture — a +0.014ms difference, within measurement noise, against a 16.67ms frame budget at 60fps. rAF cadence stayed pinned at 60fps/16.67ms in both cases (vsync-capped, not diagnostic on its own — the JS-time figure is the real signal). Conclusion: the existing coarse `Math.abs(dx) > maxDist` reject plus per-sprite billboard projection is cheap enough that placement count is not a near-term perf concern at Floor-1-scale batches; no further optimization needed unless a future floor pushes toward many hundreds of simultaneous candidates.
- Combat encounters play an FF6-style HDMA window-mask swirl via `engine/battle-transition.ts` (soft flash + spiral aperture to black, then combat; leave via `leaveCombat(next)` dissolve). `startCombat`/`leaveCombat` are serialized on a promise chain and the overlay uses a generation counter so overlapping reveals cannot hide a newer wipe. Input is gated on `combatTransitionActive` until the reveal settles — including game_over / perk / ending / arena listeners (not only dungeon/combat).
